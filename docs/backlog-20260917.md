# Backlog — 17 сентября 2026

Приоритизированный список доработок после ревью MVP Career Evidence OS.
Стек: Next.js 16 App Router, Supabase Auth, Prisma (`career_os`), Anthropic, деплой на Vercel
([carrer-os-three.vercel.app](https://carrer-os-three.vercel.app/)).

**Как читать.** P0 — продакшен сломан или пользователь не может войти. P1 — конверсия с лендинга
и обещанный «быстрый результат». P2 — качество этого же сценария. P3 — продукт вокруг evidence OS.
P4 — фундамент (деньги, аналитика, тесты, юр. страницы). Админка (разделы за логином) не
переделывается: только точечная стыковка тёмной темы с новым лендингом.

**Вне скоупа этого цикла.** Переписывание Evidence / Tracks / Pipeline / Fit Report; админ-редизайн;
массовый auto-apply; OAuth (пока не нужен для починки входа); нативные приложения.

## P0 — Продакшен: починить авторизацию на Vercel

Без этого нельзя честно звать людей на [carrer-os-three.vercel.app](https://carrer-os-three.vercel.app/).
Проверять нужно **все** каналы: пароль, magic link, подтверждение email после signup.

### P0.1 — Сессия после callback не переживает редирект

**Где.** `src/app/auth/callback/route.ts` вызывает `exchangeCodeForSession` через
`createSupabaseServerClient()` (`cookies()` из `next/headers`), затем делает `NextResponse.redirect`.
На Vercel Set-Cookie с такого ответа часто **не попадает** на редирект — классический баг
Supabase SSR + App Router.

**Что сделать.**

- Собрать cookie-адаптер, который пишет cookies **на объект redirect-ответа**, а не только в
  `cookies()` store.
- Учитывать `x-forwarded-host` / `x-forwarded-proto` (Vercel), не полагаться только на `origin`.
- Санитизировать `next`: только относительный путь своего origin, иначе open redirect.
- Покрыть vitest/integration: code → Set-Cookie на 302 → следующий запрос видит пользователя.

**Критерий готовности.** Magic link и письмо-подтверждение, открытые на проде, оставляют
авторизованную сессию и ведут в приложение.

### P0.2 — Identity-bridge: логин «успешен», приложение падает

**Где.** `supabase/sql/001_auth_sync_and_rls.sql` **не является Prisma-миграцией** — его нужно
применять руками. `getCurrentUser()` (`src/lib/auth/session.ts`) при наличии `auth.users` и
отсутствии `career_os.users` **кидает** `UnauthorizedError`, а не редиректит на логин.
`error.tsx` / `global-error.tsx` нет → пользователь видит 500. Это выглядит как «авторизация
не работает».

**Что сделать.**

- Проверить на проде, что триггер `on_auth_user_created_career_os` и FK на `auth.users` применены.
- Добавить идемпотентный backfill: если auth-юзер есть, а `career_os.users` + `credit_accounts`
  нет — создать (и в триггере, и безопасным server-side fallback, чтобы один пропущенный SQL
  не валил продукт).
- Не бросать необработанный exception: нет профиля → понятный экран «аккаунт создаётся / напишите
  нам», плюс `error.tsx` в `(app)` и корне.
- Smoke-тест: новый signup создаёт обе строки.

**Критерий готовности.** Свежий аккаунт на Vercel открывает `/dashboard` без 500.

### P0.3 — `NEXT_PUBLIC_APP_URL` и Redirect URLs в Supabase

**Где.** `src/lib/env.ts` по умолчанию ставит `http://localhost:3000`. Signup и magic link
собирают `emailRedirectTo: ${NEXT_PUBLIC_APP_URL}/auth/callback`. Если переменная не задана в
Vercel — письма уводят на localhost. Даже если задана, в Supabase Auth → URL Configuration
должны быть:

- Site URL = `https://carrer-os-three.vercel.app`
- Redirect URLs: `https://carrer-os-three.vercel.app/auth/callback`, preview-домены `*.vercel.app`

**Что сделать.** Чеклист в README: Vercel env (включая `NEXT_PUBLIC_APP_URL`, `DATABASE_URL`,
`ANTHROPIC_API_KEY`) + Supabase URLs. Убрать молчаливый default на localhost в production
(`NODE_ENV === "production"` → fail build, если URL не https продакшен-домена). Не коммитить
секреты; `.env` в репозиторий не попадает.

**Критерий готовности.** Письмо с прода содержит `https://carrer-os-three.vercel.app/auth/callback?...`.

### P0.4 — Signup и login игнорируют реальное состояние сессии

**Где.** `signUpWithPassword` всегда `redirect("/onboarding")`. Если в проекте включено Confirm
email, сессии ещё нет → proxy шлёт на `/login`, пользователь думает, что регистрация сломалась.
`signInWithPassword` всегда `redirect("/dashboard")` и **игнорирует** `?next=` (а proxy как раз
ставит `?next=/dashboard` — проверено на проде).

**Что сделать.**

- После signup: если сессии нет — экран «проверьте почту», не онбординг.
- После login: редирект на безопасный `next`, иначе `/dashboard`.
- Не пускать в `(app)`, пока email не confirmed (если confirmation включён).
- Показать на `/login` ошибку из `?error=auth_callback_failed` (сейчас параметр есть, UI его нет).
- Восстановление пароля (`resetPasswordForEmail` + страница нового пароля).

**Критерий готовности.** Новый пользователь понимает, что делать после signup; возврат с
защищённой страницы после логина приводит туда же.

### P0.5 — Дыры в proxy и cookie-refresh

**Где.** `src/proxy.ts` синхронный, хотя `updateSupabaseSession` async — явно сделать
`export async function proxy`. В `PROTECTED_PREFIXES` нет `/quick-tailor` и `/interviews`
(тест даже считает `/resources` публичным, хотя страница живёт в `(app)` и требует сессию).
Защита фактически держится на `requireCurrentUser()` в layout: редирект на `/login` **без**
`next`, плюс лишний round-trip.

**Что сделать.** Единый список защищённых префиксов, совпадающий с `(app)`: `/quick-tailor`,
`/interviews`, `/resources`. Тесты обновить. Проверить, что chunked cookies Supabase
(`sb-*-auth-token.0`, `.1`) копируются на request и response. Убедиться, что publishable-ключ
Supabase (`sb_publishable_…`) совместим с `@supabase/ssr` на Vercel; при сомнении — JWT anon key
в `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

**Критерий готовности.** Незалогиненный запрос на любой экран приложения → `/login?next=…`;
залогиненный — сессия обновляется, не выкидывает через час.

### P0.6 — Минимальная диагностика

Пока Sentry DSN пустой (`src/instrumentation.ts` no-op), ошибки auth на Vercel невидимы.

- Включить Sentry на проде (без PII резюме в payload).
- Структурный лог auth-событий: signup/login/callback success|fail + код ошибки Supabase,
  **без email/токенов**.
- Короткий runbook в README: «логин на Vercel не работает — проверить P0.1–P0.5 в таком порядке».

## P1 — Лендинг: стиль tekki + честный вход в экспресс-тюнинг

Референс визуала: [tekki.webflow.io](https://tekki.webflow.io/). Сейчас `/` — светлый serif-hero,
`max-w-4xl`, три одинаковые Card. Нет шапки, футера, motion, акцентного цвета. Это не конкурент
и не «витрина» для ICP 45+/руководителей, которым нужен уверенный, живой, тёмный first screen.

Админку не трогаем, кроме P1.5.

### P1.1 — Тёмная маркетинговая оболочка в духе tekki

**Визуальный язык (адаптация, не копия):**

- Фон: почти чёрный / глубокий navy, не slate-blue.
- Акцент: яркий жёлтый (кнопки, точки, underline, геометрические пятна), высокий контраст.
- Типографика: очень крупные гротеск-заголовки (тяжёлый вес, переносы, 2–4 слова на строку),
  не Source Serif в герое. Цифры/короткие лейблы — как «3 мин», «×3», «JOIN».
- Геометрия: крупные абстрактные формы / кольца / повторяющийся паттерн CTA на фоне
  (у tekki — WAITLIST/JOIN), но со своим словом: например «ДОКАЗАТЬ» / «FIT» / «ФАКТЫ» —
  без детских эмодзи-фестивалей, ICP старше.
- Много воздуха, мало рамок. Карточки — тёмные панели, не белый shadcn Card.
- Шапка-стек: логотип, якоря (Как это работает / Экспресс-тюнинг / Для кого / FAQ), Войти,
  жёлтый «Начать».
- Футер: контакты, политика, оферта (заглушки ок, страницы — в P4).

Отдельный `(marketing)/layout.tsx`: тёмная тема **принудительно** на `/`, `/login`, `/signup`,
будущем гостевом `/try`. Не наследовать app-shell.

**Критерий готовности.** Первый экран с телефоном и десктопа узнаваемо «тёмный + жёлтый + крупный
тип», а не текущий светлый шаблон.

### P1.2 — Структура лендинга под конверсию в экспресс-тюнинг

Собрать страницу как витрину **одного** обещания: «за три шага — резюме под вакансию, без
онбординга». Полный Evidence OS — второй экран, не первый.

Предлагаемые блоки (сверху вниз):

1. Hero: оффер + жёлтый CTA «Адаптировать резюме» (ведёт в P1.3) + вторичный «Войти».
2. Как это работает — 3 шага, как сейчас, но с визуальным мокапом результата (до/после буллета,
   не три иконки).
3. Интерактивный тизер / sticky CTA.
4. Почему не универсальное резюме (ATS, 10 секунд рекрутера) — без выдуманных «12 000 пользователей»,
   пока нет своих цифр. Формулировки в духе продукта: факты, не вымысел.
5. Для кого: GM / COO / CMO / fractional — 3–4 коротких сценария.
6. Чем отличается полная база доказательств (Evidence, fit по 10 измерениям, воронка) — мост
   в «настоящий» продукт для тех, кто останется.
7. FAQ (адаптация без выдумки? PDF? сколько вакансий? что с данными?).
8. Финальный жёлтый CTA.

Связать копирайт с правдой: **не писать «без регистрации»**, пока гостевой проход не сделан
(P1.3). Либо сделать гостевой проход, либо честно: «войти за 30 секунд, онбординг не нужен».

### P1.3 — Гостевой (или почти гостевой) вход в экспресс-тюнинг

Сейчас `/quick-tailor` за `(app)/layout.tsx` → `requireCurrentUser()`. CTA лендинга врёт.

**Что сделать** (предпочтительный продуктовый вариант):

- Публичный мастер `/try` (или `/quick-tailor` вынести из app-shell): шаги 1–2 (резюме + вакансии)
  **без аккаунта**.
- Перед генерацией — лёгкий signup/login (email), чтобы списать кредиты, сохранить результат и
  соблюсти safety/audit. Онбординг **не** запускать: после signup из `/try` → сразу шаг «Результат».
- Альтернатива, если нужен zero-friction как у Сопровода: 1 бесплатная генерация по anonymous
  session + email только на скачивание. Это сложнее (лимиты, злоупотребления) — закладывать как
  P1.3b, не блокировать P1.3.

Лендинговая кнопка «Попробовать экспресс-тюнинг» → `/try`, не `/signup`.

### P1.4 — Починить CTA-кнопки лендинга

`Button render={<Link href="/login" />}` даёт `role=button`. На проде клик «Войти» не
навигировал. Сделать настоящие `<Link>` / `nativeButton={false}` так, чтобы в a11y-дереве
были `role=link`, работал cmd-click и клавиатура.

### P1.5 — Тёмная тема админки: только токены, не лейаут

В `src/app/globals.css` блок `.dark`:

- фон/карточки ближе к navy лендинга;
- `--primary` / ring / sidebar-accent — тёплый жёлтый вместо голубого `oklch(… 258)`;
- не менять сетку сайдбара, компоненты, светлую тему (если админка по умолчанию светлая —
  оставить; стыковка нужна тем, кто включит dark).

Переключатель темы в topbar — мелкий бонус, не обязателен в P1.

## P2 — Экспресс-тюнинг до уровня «Умный отклик»

Референс: [soprovodai.ru/smart-apply](https://soprovodai.ru/smart-apply).
Текущий мастер: `src/components/quick-tailor/quick-tailor-wizard.tsx` +
`src/lib/actions/quick-tailor.ts` + `src/lib/ai/tasks/generate-quick-tailor.ts`.

Сохранить наши инварианты: **не выдумывать факты**, кредиты, `AiRun`, цитирование только
данного текста.

### P2.1 — Матрица соответствия до генерации резюме

Как у Сопровода: разбор вакансии × резюме → полное / частичное / нет информации + цитата из
резюме и комментарий.

- Новый AI-шаг (дешевле, чем полный tailor): список требований, покрытие, ключевые слова.
- UI: таблица требований, счётчик «N из M», без фейковых ATS-% пока нет своей методики.
- На этом шаге пользователь решает: адаптировать / взять другую вакансию / ответить на уточнения.

Данные сохранять у Opportunity (`OpportunityRequirement` уже есть — переиспользовать, не плодить
параллельную модель без нужды).

### P2.2 — Уточняющие вопросы вместо выдумки

Если требование «нет информации» или «частично» — 2–4 коротких вопроса («за какие метрики
отвечали лично?», «размер команды?»). Ответы — **единственный** легальный способ добавить факты
в адаптированное резюме. Пропуск вопроса = пробел остаётся пробелом.

Это главная дифференциация vs «просто перепиши резюме».

### P2.3 — Результат как документ, а не как changelog

Сейчас на шаге 3: буллеты «что изменено» + textarea письма + кнопки скачать. Превью
структурированного резюме есть только на `/resumes/.../versions/...`.

- На шаге результата: колонка резюме (как `ResumeContentPreview`, но визуально ближе к странице
  резюме) + колонка письма + список изменений с привязкой к требованию вакансии.
- Редактирование summary/буллетов до экспорта.
- Скачать письмо отдельно (txt/docx), копировать в буфер.
- Не класть весь исходный текст в `summary` (`runQuickTailor` сейчас так делает) — парсить в
  `ResumeContent` (роли, даты, буллеты) на шаге загрузки.

### P2.4 — Вход данных как у рынка

- PDF + DOCX (в продукте PDF на импорт опыта уже «best-effort в плане», в quick-tailor явно
  «не поддерживается»).
- URL вакансии (safe-fetch уже есть для Opportunities) + paste.
- Одна вакансия как счастливый путь; 2–3 — secondary («сравнить»). Батч 3 × Opus — дорого и
  медленно (см. P4.2).

### P2.5 — Состояние ожидания и стоимость

- Прогресс по шагам модели: «разбираем вакансию» → «сверяем с опытом» → «собираем резюме и письмо».
- Честно показать списание кредитов **до** кнопки (сейчас ≈3 за вакансию, сюрприз после).
- Если `not_configured` / `insufficient_credits` — отдельный экран, не throw в wizard.
- Таймаут/повтор без повторного дебета (refund уже есть в `runAiTask` — убедиться, что UI это
  переживает).

### P2.6 — После результата — мост в полный продукт

Не бросать пользователя в пустой Dashboard. Один экран: «сохранено в возможности X, версия
резюме Y. Дальше: fit-отчёт / добавить в pipeline / разобрать опыт в Evidence». Чеклист
онбординга не навязывать.

### P3.6 — Недособранные сущности плана

вместо хаоса» на лендинге обещает письма и следующий шаг — хотя бы контакт + канал на
Application, без CRM.

### P3.7 — Evidence и треки: маршруты плана

План обещает `/evidence/[id]`, `/tracks/[id]`. Сейчас только список + диалог. Для MVP списка
хватает; когда карточка вырастет (gap-suggestions, reusability) — вынести на отдельную страницу.
Не блокирует запуск экспресс-тюнинга.

### P3.8 — Экспорт резюме

PDF — ручная вёрстка pdf-lib, DOCX — `docx`. После P2.3 сверить, что экспорт совпадает с превью
(кириллица уже через PT Sans). Добавить имя файла из «Роль — Компания», не `Загруженное резюме
(черновик)`.

## P4 — Фундамент: деньги, модель, качество, доверие

### P4.1 — Кредиты как продукт

Старт: 20 кредитов с триггера, списание есть, **пополнить нельзя**. Settings только показывает
баланс. Для платящего self-serve: пакеты (разовые), экран «недостаточно кредитов» с CTA,
webhook провайдера. Пока оплаты нет — не звать это «usage-based monetization» на лендинге.

Первая адаптация бесплатно (как у Сопровода) хорошо стыкуется с P1.3.

### P4.2 — Стоимость и модель LLM

`AnthropicProvider` использует `claude-opus-5` на **все** задачи, включая parse и quick-tailor.
Экспресс-тюнинг × 3 вакансии × opus убьёт и latency, и маржу.

- Маршрутизация: Haiku/Sonnet на extract/parse/match, Sonnet (или Opus) на финальный текст резюме
  и письма.
- `maxTokens: 6144` на tailor — ок, но кэшировать повтор того же inputHash (поле уже пишется,
  повторного использования нет).

### P4.3 — Аналитика north-star

`track()` → `console.log`. Нужен реальный sink (PostHog/Amplitude) с теми же event-именами.
События воронки лендинга: `landing_cta_click`, `try_started`, `try_generated`, `signup_from_try`.
North-star из плана (14 дней, трек, 3 evidence, 2 opportunity, 1 quality action) — дашборд
для себя, не для пользователя.

### P4.4 — Тесты, которых нет по плану

Vitest закрывает схемы, fit-rules, ownership, middleware path list. Нет Playwright на
онбординг → evidence → opportunity → fit → accept proposal → pipeline. Добавить хотя бы:

- auth redirect (уже частично);
- guest `/try` → signup → результат;
- callback cookie (P0.1).

### P4.5 — Юридическое и доверие (152-ФЗ)

Резюме — персональные данные. Нет `/privacy`, `/terms`, cookie-баннера, оферты. Для публичного
лендинга с загрузкой файла это блокер рекламы, не «потом». Коротко: какие данные, зачем,
Anthropic как процессор, срок хранения, как удалить аккаунт (удаление через cascade с
`auth.users` уже заложено — нужна кнопка в Settings).

### P4.6 — README и операционка

README всё ещё create-next-app + копипаста фаз плана. Нужен: env, `pnpm db:deploy`, SQL
триггера, Vercel settings, как прогнать seed, как проверить auth.

### P4.7 — Observability файлов

Загрузка в private bucket `career-os-documents` через service role. Проверить, что bucket
существует на проде и signed URL не утекает. PDF-парсинг опыта — в плане, в UI отказ.
